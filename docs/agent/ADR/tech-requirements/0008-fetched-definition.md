# ADR tech-requirements-0008: 「取得済み」を D1 の有無で決められず、前回の取得で上位にあった 5 件の post_id に行き当たるまでめくる形で 9-13 を確定した

- **Status**: 有効
- **Date**: 2026-11-01
- **対象**: docs/agent/tech-requirements.md — 入力元の対応表、3 の境界値、4-1・4-2、5-3・5-7・残高切れ、7 の判定 1、8 の作業 2・3、9-13
- **出典**: issue #63（親 #57）、[ADR tech-requirements-0007](0007-x-api-entry.md)、利用者の判断（2026-11-01）、https://docs.x.com/x-api/users/get-liked-posts

## それまでの結論

[ADR tech-requirements-0007](0007-x-api-entry.md) が入口を X の API に替えたとき、「取得済み」の定義と持ち方を 9-13 の未確定として残していた。本 ADR がそれを確定に替える（0007 は取り消さない）。本文は次の形だった。

- 3 の境界値: 「取得済み（定義は 9-13）なら保存せず、Jev も呼ばない。1 時間おきに最新 5 件を取るので、新しいいいねが無い回は毎回起こる。保存して D1 から消した投稿（5-19）と、捨てた非 IT 系も、取得済みとして扱う」
- 5-3: 「最新 5 件（`max_results=5`）。5 件とも未取得なら次のページも取る」
- 9-13: D1 の有無では決められない。(a) 非 IT 系と判定失敗の投稿は D1 に書かないので毎時「未取得」に見え、Jev の再判定と次のページの取得が毎回起こる。(b) 5-19 の保存で D1 から消えた投稿が `liked_tweets` の最新 5 件に残り、判定し直されて翌日のバッチに重複する。(c) D1 が空の初回に「次のページも取る」の止まる場所が決まっていない。最後に見た最新のいいねの `post_id` を持つ形が候補だが、4-2 に列が無い

## 何が起きたか

#59 で 9-13 に残した (a)〜(c) を、Worker A の実装（8 節の作業 3）の前に決める必要があった。利用者が 2026-11-01 に決めた。取得は Design Doc のまま 1 時間おき。前回の取得で上位にあった `post_id` を数件 D1 に覚え、新しい順に 5 件ずつめくって行き当たったら止める。ページ数に上限を置き、初回は 1 ページで止める。一度取り消して再びいいねした投稿が再び取り込まれることは許す。

## 新しい結論

- 取得済みは、覚えた 5 件の `post_id` に新しい順にめくって行き当たった位置以降の投稿。D1 の有無では決めない。取り込んだか捨てたかを問わず、取得が済んだ回に最初のページの 5 件で覚えを置き換える
- ページ内に覚えた `post_id` が 1 件でもあればそこで止め、無ければ次のページを取る。ページは最大 3。覚えが空の初回は 1 ページで止める
- 件数 5 は、1 ページ分をそのまま覚えられて追加の読み出しが無く、5 件が同時に取り消される回はめったに無いため。上限 3 は、1 時間に 15 件までを取りこぼさず、覚えが全部取り消された回の追加の課金を約 1.5 円に抑えるため
- 許す: 取り消しと再いいねでの再取り込み、覚えが全部取り消された回の最大 15 件の過去の取り込み、1 時間に 16 件以上のいいねの取りこぼし、捨てた投稿が取り直されないこと
- Design Doc は変えていない。Design Doc 6「入口」の「5 件とも未取得なら次のページも取る」は、行き当たらないことを「未取得」と読めば同じ止め方になる。初回だけ字義どおりなら次のページへ進むので食い違い、9-13 に記録した。Design Doc に返すかは人が決める

## 影響

- 4-2 に覚える表 `seen_likes`（`post_id`、`position`）を足した。5-8 の確定と 5-19 の削除は触らない
- 入力元の対応表、3 の境界値、4-1、5-3（検査に止まり方と覚えの更新を足した）、5-7（判定し直されないこと、再いいねで再び取り込まれることを足した）、残高切れ（捨てた投稿は取り直されない。却下案の理由）、7 の判定 1、8 の作業 2・3（`seen_likes` のスキーマと migration を足した）を合わせた
