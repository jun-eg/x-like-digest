## 1. Overview（この文書が引き受ける範囲）

### 引き受ける範囲

Design Doc 7 の完了の定義を引用する。数字は書き換えない。

1. IFTTT から Worker A に届き、IT 系だけが D1 に重複なく溜まる
2. Worker B と C を分け、18:00 の Cron で日次 Markdown が生成できる
3. 保存して D1 の対象が消えるまで、正常系が最後まで動く
4. 保存障害と期限切れの挙動が検証済み
5. ログを最小化し、無料枠と実費を確認し、受け入れ試験が通る

6 の「1 週間運用して、どちらが効いているかを見る」は運用の観察であり、この文書は測り方（7）だけを持つ。

### 引き受けない範囲

Design Doc 6 のスコープ外をそのまま引く。広げない。

- X API への直接課金、公式 Activity API
- 自宅サーバー、ポート開放、Cloudflare Containers や VM による隔離
- 画像・動画の解析、リンク先本文の取得
- 過去のいいねの一括取り込み
- プロンプトインジェクションの事前検出、Jev による要約品質の判定
- 要約の再生成、複数候補の比較、人の承認フロー
- 原文全件の永続保存、PDF 生成、メールや Slack への通知、管理画面
- いいね台帳
- ダイジェストを開発環境へ取り込む自動化
- 複数利用者、共有、公開

この文書で新しく足した対象外は無い。

## 2. 実行形態と前提

動かす相手は利用者本人 1 人で、本人が実装者でもある（Design Doc 3「裏付けの限界」）。
前提知識が振れる相手は居ないので、セットアップに開発者向けの道具を要求してよい。

| 決めること | 決めたこと | 縛っている上流の行 |
| --- | --- | --- |
| 実行環境 | Cloudflare Workers（Free）3 本、D1（Free）1 本、AI Gateway 経由の TypeSafe Jev（`typesafe/jev`）。Jev は Workers AI のモデルではなく、支払いは Cloudflare のクレジットに一括する。常駐プロセスを持たない | Design Doc 2・5「固定費 $0、自宅サーバー無し」 |
| 公開面 | Worker A の `POST /webhooks/x-like` だけ。Worker B・C は公開ルートも `workers.dev` も無効 | 6「入口」「権限分離」 |
| 秘密の置き場 | IFTTT の共有シークレットは Worker A、GitHub トークンは Worker B、Claude API キーは Worker C に、それぞれ Cloudflare Secret として置く。1 つの Worker に 2 つ以上置かない | 6「権限分離」 |
| セットアップに要求するもの | Node（`.node-version` の版）、wrangler、Cloudflare・IFTTT・GitHub・Claude API の各アカウント。IFTTT の Applet と GitHub のリポジトリ・トークンは利用者が導入時に作る | 6「前提にしている『すでにあるもの』」 |
| コードの置き場 | このリポジトリ 1 本。`workers/ingest`、`workers/orchestrator`、`workers/summarizer` の 3 プロジェクト | 6「権限分離」（→ 6-2） |
| 投稿本文が通る経路 | X → IFTTT → Worker A → AI Gateway（Jev）→ D1 → Worker B → Worker C → Claude API。保存されるのは D1（要約まで）と GitHub（ダイジェストのみ）。ログには通さない | 6「運用」、Design Doc 5「原文全文を残す」の却下 |
| 時刻 | 内部は UTC で持つ。JST への変換はバッチの日付（ファイル名とジョブ ID）を決めるときだけ行う | 3-2、3-3 |

## 3. 業務の規則

この文書は規則を発明しない。出どころは要件定義書（記録）か Design Doc の判断に限る。

| # | 規則 | 適用の順序 | 出どころ |
| --- | --- | --- | --- |
| 1 | IT 系とは、ソフトウェア開発、プログラミング、AI、データベース、ネットワーク、クラウド、セキュリティ、IT 製品・技術ニュースの投稿を指す。判定は本文テキストだけで行う | 構造検証を通った投稿ごとに 1 回 | 要件定義書 FR-03.2・FR-03.7（記録） |
| 2 | 「その日の投稿」とは、その日の 18:00 JST までにシステムが受信して D1 に保存した、まだどのバッチにも属さない投稿の集合。いいねした時刻や投稿の作成日では絞らない | 本処理の最初に 1 回 | 要件定義書 FR-05.4・FR-05.5（記録）、Design Doc 6「確定」 |
| 3 | ダイジェストの日付とファイル名は、本処理を行った日の JST 日付 | バッチ確定時に決めて、以後変えない | 要件定義書 FR-07.2（記録） |
| 4 | 同じ日付のファイルが GitHub に既にあり、内容が同じなら保存済みとして扱う。内容が違えば上書きせず競合として扱う | 保存の前と、応答が失われたときの確認時 | 要件定義書 FR-07.8（記録） |
| 5 | 削除するのは今回のバッチに属する投稿だけ。バッチに属していない投稿は消さない | ジョブが終端状態になったとき | 要件定義書 FR-09.1・FR-09.4（記録） |
| 6 | 要約は 1 回だけ。GitHub 保存の再試行は翌日の本処理まで。それを過ぎたらバッチの投稿と Markdown を捨てる | 保存が失敗するたびに次回を決め、期限で打ち切る | Design Doc 6「要約」「再試行」 |
| 7 | 対象が 0 件の日は Claude を呼ばず、GitHub に空のファイルも作らない | バッチ確定の直後 | 要件定義書 FR-05.6（記録） |

### 境界値と特別扱い

| 入力の形 | どう扱うか | 出どころ |
| --- | --- | --- |
| 18:00:00 JST ちょうどに受信した投稿 | `received_at` が当日 09:00:00 UTC 以下ならその日のバッチ。超えていれば翌日 | 規則 2 の「18:00 まで」を閉区間に読む。要件定義書 FR-05.4 |
| Cron が遅れて 18:00 より後に本処理が動いた | バッチの範囲は実行時刻ではなく 09:00 UTC で切る。遅れて届いた投稿は翌日に回る | 要件定義書 FR-05.5（記録） |
| 同じ `post_id` を複数回受信 | 2 回目以降は保存せず 2xx を返す。IFTTT の再送を想定する | 要件定義書 FR-02.6・§7.1（記録） |
| `tweet_url` のホストが `twitter.com` | `x.com` と同じ正規ホストとして受ける。それ以外のホストは 400 | 要件定義書 FR-02.5（記録） |
| Jev が時間切れ・失敗・形式不正 | 保留せず捨てて 2xx を返す。再試行は求めない | 要件定義書 FR-03.5（記録） |
| 要約の入力が Claude の上限を超える | バッチを失敗扱いで捨てる。一部だけ切り捨てて要約しない | 要件定義書 FR-06.12（記録） |
| GitHub の `Retry-After` が期限（翌日 09:00 UTC）を超える | 次回は期限ちょうどにして最終試行とし、それでも失敗なら捨てる | Design Doc 6「再試行」、要件定義書 FR-08（記録） |
| 保存の応答が失われた（タイムアウト） | 同じパスを GET して内容一致なら成功扱い、不一致なら競合、無ければ失敗として再試行 | 要件定義書 FR-07.6・FR-08（記録） |
| 前日のジョブが未保存のまま翌日の本処理に入った | 前日分の最終試行を先に行い、失敗なら捨てる。そのあとで当日のバッチを確定する。前日分の投稿は `batch_id` が付いているので当日分に混ざらない | Design Doc 6「再試行」 |
| D1 の削除が失敗した | ジョブは終端状態のまま残し、次の Cron で同じ `batch_id` の削除を再実行する | 要件定義書 §8 最終行（記録） |

### 4-1. 受信 JSON（要件定義書 FR-01.4・§3「Webhook 受信 JSON」・§7.1）

| # | 項目 | 形式 | 必須 | 実体（正規表現・選択肢・既定値） | 在処 |
| --- | --- | --- | --- | --- | --- |
| 1 | `text` | 文字列 | 必須 | 投稿本文。IFTTT の `Text` | FR-01.4、§3 |
| 2 | `author` | 文字列 | 必須 | 投稿者ユーザー名。IFTTT の `UserName` | 同上 |
| 3 | `tweet_url` | URL 文字列 | 必須 | IFTTT の `LinkToTweet`。ホストが `x.com` か `twitter.com`（`www.` 付きを含む）で、パスが `/<name>/status/<数字>` に一致するものだけ | FR-02.5 |
| 4 | `first_url` | URL 文字列 | 任意 | 本文中の最初のリンク。IFTTT の `FirstLinkUrl` | FR-01.4 |
| 5 | `created_at` | 日時文字列 | 任意 | 投稿の作成日時。いいねした日時ではない。IFTTT の `CreatedAt` | FR-01.4、§3 注 |

| 2 | `text` | 文字列 | 必須 | 受信 JSON の `text` | FR-04.2 |

### 4-3. ジョブ状態（要件定義書 §4）

| # | 状態 | 意味 | 次の動作 | 在処 |
| --- | --- | --- | --- | --- |
| 1 | `PROCESSING` | 18:00 の要約処理中 | Claude の結果待ち | §4 |
| 2 | `READY_TO_PUBLISH` | 要約検証済みで GitHub 保存待ち | 保存試行 | §4 |
| 3 | `PUBLISHED` | GitHub 保存済み | 対象投稿削除、メタ情報保持 | §4 |
| 4 | `ABANDONED` | 要約失敗または GitHub 保存を打切り | 対象投稿・下書き削除 | §4 |
| 5 | `SKIPPED` | 対象 0 件 | 処理終了 | §4 |

ジョブ ID は JST 日付をキーとし、一意制約を持つ（§4）。削除後も残す実行履歴は、ジョブ ID、処理日、投稿件数、最終ステータス、試行回数、コミット SHA、終了日時、エラー種別で、本文を含まない（FR-09.5）。

### 4-4. GitHub 保存（要件定義書 FR-07・§7.3）

| # | 項目 | 実体 | 在処 |
| --- | --- | --- | --- |
| 1 | パス | `daily/YYYY-MM-DD.md` | FR-07.2 |
| 2 | API | `PUT /repos/{owner}/{repo}/contents/daily/{YYYY-MM-DD}.md`。本文は Base64。更新時は既存の blob SHA が要る | §7.3 |

## 5. 仕様

上流の判断 1 つにつき、観測できる帰結を並べる。

| # | 上流の判断 | 帰結の仕様（観測できる形） | 判定のしかた |
| --- | --- | --- | --- |
| 1 | 入口は公開 Webhook 1 本 | Worker A は `POST /webhooks/x-like` 以外に 405 か 404 を返す | 自動テストで `GET /`、`POST /other` を送る |
| 2 | 共有シークレットで認証 | `Authorization: Bearer <秘密>` が一致しない要求は 401 で、D1 に書かない | 自動テストで誤った値・無しを送り、D1 の件数が増えないことを数える |
| 3 | JSON を検証 | Content-Type が `application/json` でなければ 415、Body が 16 KiB を超えれば 413、4-1 の形に合わなければ 400。想定外フィールドも 400 | 自動テストで各ケースを 1 件ずつ送る |
| 4 | `tweet_url` を厳密に解析 | 4-1 の 3 の条件を URL 解析で判定する。前方一致ではない。`post_id` は数字文字列のまま D1 に入る | 自動テストに `https://x.com.evil.example/…`、`https://x.com/a/status/abc` を含めて 400 を数える |
| 5 | Jev で IT 系だけを残す | Jev の `noul` 型の true/false 質問で判定し、スコアが閾値以上なら保存、未満なら捨てて 2xx | 自動テストでは Jev を差し替えて両方の分岐を通す。実機は 7 の判定 1 |
| 6 | 判定失敗は捨てる | Jev の時間切れ・例外・形式不正で D1 に書かず 2xx を返す。再送を求めない | 自動テストで Jev を失敗させて D1 の件数を数える |
| 7 | 重複は冪等 | 同じ `post_id` を 2 回送っても D1 は 1 行。2 回目も 2xx | 自動テストで同じ Body を 2 回送って `COUNT(*)` を取る |
| 8 | 18:00 JST に未処理を 1 バッチに確定 | ジョブ ID は JST 日付。確定は 1 文の `UPDATE posts SET batch_id = ? WHERE batch_id IS NULL AND received_at <= ?`（? は当日 09:00:00 UTC）で行う | 自動テストで 09:00 UTC の前後に `received_at` を置いた投稿を用意し、前だけが付くことを数える |
| 9 | 0 件なら何もしない | 確定件数が 0 ならジョブを `SKIPPED` にし、Worker C を呼ばず GitHub にも書かない | 自動テストで Worker C と GitHub の呼び出し回数が 0 であることを数える |
| 10 | 二重起動しない | ジョブ ID の一意制約で 2 回目の確定は失敗し、投稿に 2 つ目のバッチが付かない | 自動テストで同じ日付の本処理を 2 回走らせ、ジョブが 1 件であることを数える |
| 11 | Worker B が Service Binding で Worker C を呼ぶ | Worker C は `summarize({ posts, digestDate })` を受けて `{ markdown }` を返す。公開ルートを持たない | 自動テストで Worker C に直接 HTTP を送って到達しないことを確かめる |
| 12 | Claude Fable 5.1 が 1 回だけ生成 | モデル ID は `claude-fable-5-1`。`tools` を渡さない。1 バッチにつき Claude の呼び出しは最大 1 回 | 自動テストで Claude を差し替え、保存を 3 回失敗させても呼び出し回数が 1 であることを数える |
| 13 | 形式の機械検証だけ行う | 検証は 4 つ。本文が空でない。4-5 の見出し 4 本がこの順にある。空白と改行を除いた文字数が 1,000 以上 1,300 以下。本文中の `x.com` と `twitter.com` の status URL がすべてバッチの `tweet_url` に含まれる | 自動テストで各条件を 1 つずつ崩した Markdown を通して不合格を数える |
| 14 | 要約に失敗したら捨てる | Claude の失敗、応答不正、13 の不合格のいずれでもジョブを `ABANDONED` にし、バッチの投稿を削除し、GitHub に書かない | 自動テストで 3 種類を起こし、D1 の投稿が 0 件、GitHub の呼び出しが 0 回であることを数える |
| 15 | 要約を D1 に一時保持 | 13 に合格した Markdown をジョブの行に保存して `READY_TO_PUBLISH` にする。`PUBLISHED` と `ABANDONED` で NULL にする | 自動テストで各状態の行を読み、Markdown 列の有無を数える |

### 9-2 の確定内容

2026-11-01 に、`node_modules/.bin/wrangler dev`（remote の AI バインディング）で動かした一時 Worker から、`env.AI.run` で 4 回呼んで確かめた（Cloudflare の docs は `https://developers.cloudflare.com/ai/models/typesafe/jev/`）。

- モデル ID は `typesafe/jev`。応答の `model` は `jev-1.13.0`。カタログに `typesafe/jev-1.14.0` もあるが、1.14 は呼んでおらず、`noul` の 0.6 は 1.13 の応答で見ているので、版を固定せず別名の `typesafe/jev` を採る。`model` が変わったら閾値（9-1）を見直す
- 呼び方は `env.AI.run("typesafe/jev", input, { gateway: { id } })`。Worker A の AI バインディングをそのまま使い、TypeSafe の API キーも Cloudflare の API トークンも Worker A に置かない。gateway ID は `x-like-digest-jev`（Worker A の `vars` の `AI_GATEWAY_ID`。秘密ではない）。gateway 指定なしでも同じ応答が返ったが、gateway を指定すれば使用量がこの gateway に残るので指定する
- 入力は `{ state: <判定する本文>, questions: { <名前>: { type: "noul", instructions: <true/false の質問>, criteria: { true: <真の基準>, false: <偽の基準> } } } }`
- 応答は `answers.<名前> = { type: "noul", noul: <0〜1> }`、`model`、`usage`（`input_tokens`、`output_tokens`）。実機で `wrangler dev` から受けた値は、`{ "state": "Completed", "result": { この応答 } }` に包まれていた。docs の例に包みは無い。deploy した Worker で包みが付くかは未確認で、Worker A の作業 3 で zod が両方を受けるか実機で決める
- `noul` は true である確率。実機の値は、IT の投稿（Workers と D1）0.99、Rust の借用チェッカー 0.99、学園祭のたこ焼き 0.01。閾値は `noul >= 0.6` なら保存、未満なら捨てる。0.6 付近の投稿は今回見ておらず、閾値の実測は 9-1 のまま
- 1 件の使用量は入力約 360 トークン（質問の分を含む）、出力 21 トークンで、docs の単価（入力 1M トークンあたり $0.042）なら 1 件あたり約 $0.000015
