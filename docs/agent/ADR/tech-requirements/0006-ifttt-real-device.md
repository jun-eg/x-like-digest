# ADR tech-requirements-0006: 9-8 を実機で確定した。Body は本文を `<<<` `>>>` で囲み、12 秒には収まった

- **Status**: 取り消し（[ADR tech-requirements-0007](0007-x-api-entry.md) が上書き）
- **Date**: 2026-11-01
- **対象**: docs/agent/tech-requirements.md — 4-1、7 節の判定 1、8 節の作業 4、9 節の 8 行目と「9-8 の確定内容」
- **出典**: issue #44（親 #42）、ADR design-doc-0002、利用者の実機の記録（2026-11-01）

## それまでの結論

9-8 は「Ingredient を JSON に差し込むときのエスケープ挙動」と「応答制限 12 秒に Jev と D1 保存が収まるか」を作業 4 の実機確認待ちにしていた。

## 何が起きたか

7 節の判定 1 は、実機の合格の線を「行数が 1（IT 系の 1 件だけ）」としていた。Body を `"text":"{{Text}}"` にすると、改行を含む投稿が 400 になった（応答の種類は直接見ていない）。`"text":"<<<{{Text}}>>>"` に変えると改行を含む IT 系 2 件が保存され、D1 に改行が残った。19:34 の実行は「Action ran」で時間切れにならなかった。

## 新しい結論

- Body は本文を `<<<` と `>>>` で囲む。全文を 4-1 に書いた。トリガーは「New liked tweet by you」で、「New link by you」には `FirstLinkUrl` が無い
- 12 秒には収まった。所要時間は測っていない
- 判定 1 の線を直した。IFTTT Free は確認が 1 時間に 1 回でいいねがまとめて届き、IT 系が 1 件で済む保証がない（実際は 2 件届いて 2 行になった）ので、「行数が流した IT 系の件数と一致、非 IT 系は 0 行、同じ投稿の 2 回目で増えない」にした。この線で合格。作業 4 の「3 件」も「IT 系・非 IT 系を 1 件以上ずつ」にした
- 確かめていない: リンクの無い投稿の `first_url: ""` が 400 になるか（扱いは決めていない）、400 の理由がログに出ない点（#50）、IFTTT 自身の再送

## 影響

- 7 節の判定 1 と作業 4 を上の線に直した。4-1 に Applet の組み方と `CreatedAt` の実例（ISO ではない）を足した。コードは変えていない
