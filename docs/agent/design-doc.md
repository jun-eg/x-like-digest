## 1. Overview（概要）

X で「いいね」した投稿のうち IT 系のものだけを集め、毎日 18:00（JST）に Claude が A4 約 1 ページの日本語ダイジェストにして GitHub に積む。
集める操作は今までどおり「いいね」を押すだけで、読む側は帰宅後に 1 ページ読めばよい。
固定費 $0 の Cloudflare 無料枠で無人運用する。変動費は X の API だけで、いいねが 1 日 2〜10 件なら月 32〜68 円に収まる。

## 2. What we provide（何をつくるのか）

届ける価値は 2 つある。

- 読む側がラクになる。いいねした技術情報を、帰宅後に 1 日 1 ページで読み切れる。技術と雑談を自分で選り分けなくてよい
- 残す側の糸口ができる。何に興味を持ったかの偏りが、日付つきのダイジェストとして GitHub に積み上がる。PC からもスマホからも開ける

利用者が新しく覚える操作は無い。いいねを押す手は変えず、読む側と残す側だけが変わる。

## 3. BackGround（バックグラウンド）

### 困りごと

利用者は X で技術系の投稿を見つけると「あとで読む」のつもりでいいねを押す。
しかしいいねの一覧は時系列に溜まるだけで、読み返さない。
どこにもコンテキストとして蓄積されないので、得た情報がその後の開発や学習に活かされていない。

### そう判断した根拠

利用者本人の証言のみ（壁打ち、2026-11-01）。

### 裏付けの限界

- 利用者が 1 人で、証言も本人のものしか無い。他の人の体験には当たっていない。
  この限界は 6 の「スコープ内」に効く。MVP は利用者 1 人の運用を前提にし、複数利用者や共有は考えない
- 「読み返さない」理由が「IT 系と雑談が混ざるから」なのか「一覧が長いから」なのかは分けて聞いていない。
  この限界は 6 の「IT 系だけ残す」と「1 ページに収める」の両方に効く。どちらか片方で足りる可能性は、運用してから見る

## 4. User Story（ユーザーストーリー）

### 利用者（jun-eg）

主役はこの 1 人だけで、他の立場は居ない。

Before。日中に X でいいねを押す。帰宅後は一覧を開かない。数日経つと何をいいねしたか思い出せず、
いいねは「押した」という事実だけが残っている。興味の偏りはどこにも記録されず、自分でも言語化できない。

After。日中の操作は同じで、いいねを押すだけ。帰宅後に GitHub を開くと、その日の 18:00 までにいいねした IT 系の投稿が
話題ごとにまとまった 1 ページになっている。読み切れる量なので毎日読む。
日付ごとのファイルが積み上がるので、後から「あの頃は何に興味があったか」を辿れる。
いいねの偏りが GitHub にあることで、開発環境への取り込みなど後から活かす道が開く（活かす仕組み自体は今回作らない）。

裏付けは本人の証言。想像で埋めた部分は無い。

## 5. Alternatives Considered（検討した代替案）

| 代替案 | 内容 | 選ばなかった理由 |
| --- | --- | --- |
| ブックマークをトリガーにする | X のブックマークを収集操作にする | いいねに意味的に含まれる。好みの偏りを溜めるにはいいねのほうが向く |
| Claude で IT 系を判定する | 投稿ごとに Claude に分類させる | 1 投稿ごとに費用が掛かる |
| キーワードで IT 系を判定する | 語の一致で分類する | 日本語と英語の技術投稿を拾い漏らす可能性が高い |
| 即時に要約する | いいねのたびに要約する | 費用が投稿数に比例し、話題の集約もできない |
| 週に 1 回まとめる | 週次で要約する | 量が多く 1 ページに収まらない。帰宅後に毎日読む形に合わない |
| 原文全文を残す | 投稿本文を永続保存する | 読まない。偏りの記録はダイジェストで足りる |
| Obsidian など手元に置く | ローカルの保存庫に書く | 別の PC やスマホから開けない |
| 自宅サーバー・Cloudflare Containers | 常時稼働させる | 固定費を発生させない方針に反する |
| IFTTT Free で Webhook を送る | 「New liked tweet by you」から Worker A に POST する。当初の入口 | Applet は実機で組めたが、1 回の実行で 120 credits かかり、無料枠では月 8 件分しか流せない。1 日 1 回のダイジェストが成り立たない（ADR design-doc-0003） |
| IFTTT の有料プラン | credit を買い足して IFTTT を続ける | 利用者が IFTTT をやめると決めた |
| スマホの共有から送る | いいねした投稿を共有メニューのショートカットから Worker A に送る。本文は oEmbed で引く | 無料だが、いいねのほかに 1〜2 タップ増え、送り忘れると届かない。「いいねを押すだけ」が崩れる |
| ブラウザ拡張で拾う | PC の x.com でいいねの操作を拾って Worker A に送る | 利用者は PC のブラウザで X を使わない。画面構造が変わると壊れる |
| 要約を翌日に持ち越す | 要約に失敗した投稿を翌日のバッチに回す | その日の話題でなくなる。保留の状態管理が増える |
| GitHub 保存の再試行を 1 時間で打ち切る | 要件定義書の当初案 | Cloudflare 無料枠は再試行を縛らない。Cron の上限はアカウントで式 5 本であって発火回数ではない。翌日の本処理まで粘れる |
| いいね台帳を別ファイルで残す | 本文を含まない URL・投稿者・日付の一覧を GitHub に置く | 今回はダイジェストで足りる。後から活かす仕組みと共にスコープ外 |
| ジャーニーマップと HMW を起こす | skill の手順どおりに上流を書く | 利用者本人 1 人で証言も本人のもの。壁打ちで代える |

## 6. Functional Requirements（機能要件：MVP）

MVP は要件定義書 §12 の P1〜P5 全部である。無人運用が前提なので、再試行と冪等性を外すと「GitHub が落ちた日に黙って消える」ことになり、価値が検証できない。

### スコープ内

- 入口。Worker A が X の API（本人の `GET /2/users/{id}/liked_tweets`、owned read で 1 件 $0.001）で自分のいいねを 1 時間おきに取りに行く。1 回に取るのは最新 5 件で、5 件とも未取得なら次のページも取る。投稿者名は無認証の oEmbed で引き、API の expansions は使わない（利用者情報は 1 件 $0.01 で、投稿の 10 倍かかる）。認証は OAuth 2.0 の refresh token を Worker A が持つ。いいねから D1 に届くまで最大 1 時間かかり、18:00 の本処理はその時点で届いている分を扱う
- 分類。Worker A が Jev で IT 系かどうかを判定し、IT 系だけを D1 に保存する。非 IT 系と判定失敗は捨てる
- 確定。毎日 18:00 JST に Worker B が、その時点で D1 にある未処理の投稿を 1 バッチに確定する。0 件なら何もしない
- 要約。Worker B が Service Binding で Worker C を呼び、Claude Fable 5.1 が話題別の日本語ダイジェスト（A4 約 1 ページ、Markdown）を 1 回だけ生成する。形式の機械検証だけ行い、失敗したらその日の投稿を捨てる
- 保存。Worker B が GitHub Contents API で `daily/YYYY-MM-DD.md` に保存し、内容一致を確認してから D1 の該当バッチを消す
- 再試行。保存に失敗したら翌日 18:00 の本処理まで再試行する。cron は 10 分おき 1 本で、次に試す時刻はジョブが持つ。最初の 1 時間は 10 分間隔、以降 1 時間間隔。翌日の本処理でも未保存なら捨てる。要約は再実行しない
- 権限分離。Worker C は Claude API キーだけ、Worker B は GitHub トークンだけを持つ。Claude にツール実行権限を与えない
- 運用。本文と秘密を含まないログ、無料枠と実費の確認、受け入れ試験

### スコープ外（今回やらないこと）

- 公式 Activity API、X の API の expansions による利用者情報の取得
- 自宅サーバー、ポート開放、Cloudflare Containers や VM による隔離
- 画像・動画の解析、リンク先本文の取得
- 過去のいいねの一括取り込み
- プロンプトインジェクションの事前検出、Jev による要約品質の判定
- 要約の再生成、複数候補の比較、人の承認フロー
- 原文全件の永続保存、PDF 生成、メールや Slack への通知、管理画面
- いいね台帳（本文を含まない URL・投稿者・日付の一覧）
- ダイジェストを開発環境へ取り込む自動化。GitHub に積むのはその糸口までで、活かす仕組みは別の取り組みにする
- 複数利用者、共有、公開

MVP はスコープ外に置いたどの仕組みにも依存しない。

### 前提にしている「すでにあるもの」

| すでにあるもの | 誰が用意するか |
| --- | --- |
| X のアカウントと、いいねを押す習慣 | 利用者が持っている |
| X Developer のアカウントと OAuth 2.0 のアプリ、API のクレジット（カード登録が要る） | 利用者が導入時に作る。無料枠は無く、本人のいいねの読み取りは 1 件 $0.001 の従量課金 |
| Cloudflare のアカウント（Workers Free、D1 Free、AI Gateway のクレジット） | 利用者が持っている。Jev（TypeSafe の `typesafe/jev`）は AI Gateway 経由で呼び、支払いは Cloudflare のクレジットに一括する |
| 保存先の GitHub リポジトリと、そこに限定した書込トークン | 利用者が導入時に用意する |
| Claude API キー | 利用者が持っている |

### 埋まっていないこと（△）

- 【取り消し 2026-11-01】IFTTT Free の Applet は実機で成立したが、1 回の実行で 120 credits かかり無料枠では月 8 件分しか流せないので、入口から外した（ADR design-doc-0003）。Applet の組み方と実機の記録は ADR design-doc-0002 と技術の要件定義 9-8 に残る
- X の API の費用。公式の料金表（2026-11-01 に読んだ）で、本人のいいねは 1 件 $0.001、同じ投稿は同じ UTC 日に 1 回だけ課金。1 時間おきに最新 5 件を取る形なら、月額 ≒ 23 円（UTC の日付をまたいで上位に残る前日分 5 件 × 30 日）＋ 4.5 円 × 1 日のいいね件数（1 ドル 150 円）。利用者の目安は 1 日 2〜10 件で月 32〜68 円、17 件で 100 円の線を超える。実額は初月の請求で確かめる
- 「同じ投稿は 1 日 1 回」は公式が soft guarantee と書いていて、障害時などに成り立たないことがある。料金そのものも 2026 年に何度も変わっている。初月の実額が線を超えたら、7 の見直しで入口を再検討する
- 判定 1（IT 系だけが D1 に重複なく溜まる）は IFTTT の実機で満たしたが、入口が替わったので X の API で取り込んだ形でもう一度測る。線は技術の要件定義 7 節

Jev の閾値、Workers Free の CPU 10 ms、Claude の入力上限、GitHub の保存先の設定値は、判断は決まっていて値だけが未確定なので `docs/agent/tech-requirements.md` に送る。
